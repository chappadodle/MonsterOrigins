# Port to Minecraft 1.21.1 — Sub-project 1: Build Migration

## Context

The user wants to port this mod from Minecraft 1.20.1 to 1.21.1 and has already downloaded the
target dependency jars themselves: `fabric-api-0.116.15+1.21.1.jar`,
`Origins-1.13.0-pre.3+mc.1.21.1.jar`, and `Pehkui-3.8.3+1.14.4-1.21.jar` (the same exact jar
already used for 1.20.1 — Pehkui's own versioning already spans both).

This is a real Minecraft version bump, not a small feature: new mappings, a new Java target, and
— the biggest actual risk for this specific codebase — this mod has an extremely mixin-heavy,
decompiled-vanilla-signature-dependent history (17+ mixins, many verified against exact 1.20.1
bytecode via `javap`/CFR decompile, per this project's own extensively documented CLAUDE.md
gotchas). We can't know what's actually broken by the version bump until we try compiling against
the new mappings — so the port is split into two sub-projects:

1. **This sub-project**: migrate build config only (dependency versions, Java target, Loom
   version if needed) and attempt a build. No mixin/Java source fixes here. The deliverable is
   either a successful build (unlikely, but possible) or a complete, captured list of every
   compile error the version bump surfaced.
2. **A later sub-project**, scoped only once sub-project 1's real error list exists — fixing
   whatever actually broke, then an in-game playtest.

Investigation this session already resolved the two biggest open risk questions favorably:
- **No stable Origins release exists for 1.21.1 at all** (checked Modrinth's API directly — every
  1.21.1-targeting Origins build is alpha/beta/pre-release). The pre-release the user downloaded
  (`1.13.0-pre.3+mc.1.21.1`) is the newest available, not a corner being cut.
- **Apoli compatibility looks solid**: the pre-release Origins jar's own `fabric.mod.json` bundles
  `apoli-2.12.0-pre.3+mc.1.21.1.jar` via jar-in-jar, but its own `depends` block only requires
  `apoli: >=2.11.11` — the exact same minimum version this project already compiles against for
  1.20.1. This strongly suggests Apoli's own API surface (the part this mod's custom
  `EntityActionType` registration in `power/ScreamConeAction.java` touches) hasn't had a breaking
  version bump, even though the underlying jar itself is newer.
- All three target dependency coordinates (`origins`, `fabric-api`, `pehkui` at the versions
  above) resolve via Modrinth's maven at the same `maven.modrinth:<slug>:<version>` coordinate
  format this project's `build.gradle` already uses — no local-file/flatDir workaround needed.
- **Java 21 is now required**, not 17 — confirmed directly from the downloaded Origins jar's own
  `fabric.mod.json`, which declares `"java": ">=21"`.

Origins Minus is not a concern for this port — it was fully removed as a dependency in the
previous session's work (v2.0.0), so there's nothing to find/port a 1.21.1 build of.

## What changes

### `gradle.properties`

- `minecraft_version=1.20.1` → `minecraft_version=1.21.1`
- `fabric_api_version=0.92.11+1.20.1` → `fabric_api_version=0.116.15+1.21.1`
- `origins_version=1.10.2+mc.1.20.1` → `origins_version=1.13.0-pre.3+mc.1.21.1`
- `apoli_version=2.11.11` → `apoli_version=2.12.0-pre.3+mc.1.21.1` (matching what's actually
  bundled inside the new Origins jar, same reasoning this project's own `gradle.properties`
  comment already documents for why the apoli version is pinned to what Origins itself bundles)
- `pehkui_version=3.8.3+1.14.4-1.21` — **no change**, confirmed identical jar.
- `cardinal_components_version`/`calio_version` — attempt the build first with the existing pins
  (`5.2.2`/`1.13.3`). These are only needed as `modCompileOnly` for this project's own mixin that
  calls Origins' `OriginComponent` API (`ArthropodPassiveTargetMixin`) — only bump them if the
  build actually fails to resolve or compile against the current pins. Do not speculatively bump
  either version without a real compile error demanding it.
- `mod_version` — leave as-is (`2.0.0`); this sub-project doesn't ship a release, and the version
  number for an eventual 1.21.1 release is a separate decision for later.

### `build.gradle`

- Java compile target: find wherever this file currently sets `options.release = 17` (per this
  project's own documented "Gradle needs Java 21+ to run, but the mod compiles for Java 17" split)
  and change it to `21`, matching the new Origins jar's own `"java": ">=21"` requirement. Read the
  file directly to find the exact line before editing — do not assume its exact current syntax.
- Loom version (`loom_version` in `gradle.properties`, currently `1.17-SNAPSHOT`): attempt the
  build first with the current pin. Fabric Loom is generally not tied 1:1 to a single Minecraft
  version per release, so this may already work unchanged. If Loom itself fails to resolve
  1.21.1's version metadata (a distinct failure mode from a normal compile error — it would fail
  very early, during Gradle configuration, not during `compileJava`), bump to the newest available
  Loom release at time of implementation (check `https://maven.fabricmc.net/net/fabricmc/fabric-loom/net.fabricmc.fabric-loom.gradle.plugin/maven-metadata.xml`
  for the current list — `1.17.17` and several `1.18.0-alpha.*` builds were available as of this
  session's investigation, but this list changes; recheck rather than assume that snapshot is
  current at implementation time).
- Any other explicit version-pinned dependency declarations in this file (search for
  `modImplementation`/`modCompileOnly` lines) that reference a Minecraft-version-specific
  coordinate not already covered by a `gradle.properties` property — read the file in full to
  confirm there are no others beyond what's already covered above.

### `CLAUDE.md`

- Update the documented split ("Gradle needs Java 21+ to run, but the mod compiles for Java 17")
  to reflect that both are now 21, once the `build.gradle` change above is made — this is a
  real, load-bearing environment fact for any future session working in this repo, not just
  incidental prose (unlike the Origins Minus mentions caught in the previous port's final
  review, this one actively describes how to build the project and would mislead a future
  session if left stale).

## Explicitly out of scope for this sub-project

- Any mixin, item, effect, or other Java source fix, no matter how small or obvious the fix
  might seem once a compile error is seen. Capture the error, do not fix it here — that's
  sub-project 2's job, scoped after this sub-project's real error list exists.
- Any in-game/runtime verification. This sub-project's success criterion is about the build
  step only.
- Bumping `cardinal_components_version`/`calio_version` speculatively (see above — only bump
  if a real compile/resolution error demands it).
- Deciding the eventual 1.21.1 release's `mod_version` number.

## Isolation

Per the user's explicit choice this session: this work happens on a dedicated branch/worktree
(e.g. `mc1.21.1-port`), not directly on `master` — unlike every other change this session, a
partially-broken mid-port state is a real, likely outcome here, and `master` is what's actively
deployed to 5 PrismLauncher instances for 1.20.1 play. Use the `superpowers:using-git-worktrees`
skill (or equivalent) to set this up before any file changes.

## Verification

- `python3 -c "import json,glob;[json.load(open(f)) for f in glob.glob('src/main/resources/**/*.json', recursive=True)]"` — the JSON data pack files themselves don't change in this sub-project, but re-run anyway as a cheap sanity check that nothing was accidentally touched.
- `JAVA_HOME=<a JDK 21+ path> ./gradlew build` — the real verification. Two distinct possible
  outcomes, both are valid, complete deliverables for this sub-project:
  - `BUILD SUCCESSFUL` — genuinely possible given the reassuring Apoli-version-floor signal above,
    though not the expected case given how much of this mod's Java code depends on exact
    decompiled vanilla method signatures that may have shifted between 1.20.1 and 1.21.1.
  - A build failure with one or more compile errors — expected and fine. Capture the **complete**
    error list (every error Gradle reports in one run, not just the first) verbatim into a
    dedicated findings file (e.g. `docs/superpowers/specs/2026-08-03-port-to-1.21.1-compile-errors.md`
    or similar) as this sub-project's actual deliverable — this becomes sub-project 2's scoping
    input.
- Report back explicitly which outcome occurred, and if it's the error-list outcome, roughly how
  large/varied the error list looks (a handful of similar errors vs. dozens of unrelated ones) —
  this materially affects how sub-project 2 should be scoped/decomposed, and this headless
  environment has no other way to gauge that a future session would find useful.
