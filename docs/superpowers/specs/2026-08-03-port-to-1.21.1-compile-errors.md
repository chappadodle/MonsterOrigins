# 1.21.1 port — compile error capture

## Update (this session, continued): dependency resolution fixed

The original capture (below, kept for the record) found the build failing at Gradle's
project-configuration stage: `apoli_version=2.12.0-pre.3+mc.1.21.1` didn't resolve on JitPack
under the `com.github.apace100` group. Root cause found by checking Origins' own real
`build.gradle`/`gradle.properties` at the exact matching tag (`1.13.0-pre.3+mc.1.21.1`, via the
GitHub API): **the whole `apace100` org moved its Maven group from `com.github.apace100` to
`io.github.apace100`** for both Apoli and Calio — this isn't a JitPack quirk, it's a real
publishing change upstream. Fixed by:

- `build.gradle`: `com.github.apace100:calio:...` → `io.github.apace100:calio:...`,
  `com.github.apace100:apoli:...` → `io.github.apace100:apoli:...`
- `gradle.properties`: `calio_version=1.13.3` → `calio_version=1.14.0+mc.1.21.x` (the exact
  version Apoli 2.12.0-pre.3 itself pins, found in Apoli's own `gradle.properties` at its matching
  tag — the 1.20.1-era `1.13.3` pin was stale, unrelated to the group-id issue)

With those two changes, the build genuinely reaches `compileJava` for the first time — dependency
resolution is fully working now. **This is real, working progress**, not a dead end.

## Real compile-error result (this is sub-project 2's actual scope)

Captured from `JAVA_HOME=~/.local/jdks/temurin-21 ./gradlew clean build --continue` on branch
`mc1.21.1-port`. **100 distinct compile errors** (`--continue` output has some duplication from
independent task retries; unique error-message patterns counted below). This is real,
comprehensive 1.21.1 API breakage across items, effects, mixins, and renderers — not a mixin-only
problem as originally guessed.

### By pattern (grouped by shared root cause, most impactful first)

1. **`ResourceLocation(String, String)` constructor is now private — 68 occurrences, by far the
   largest bucket.** Every `new ResourceLocation(namespace, path)` call site in this codebase
   needs to become `ResourceLocation.fromNamespaceAndPath(namespace, path)` (the new static
   factory method 1.21 introduced). Purely mechanical — almost certainly the single
   highest-value fix in this whole list, likely resolvable with one careful project-wide
   find/replace plus a recompile to catch stragglers.

2. **Cardinal Components API's package renamed — `dev.onyxstudios.cca` → `org.ladysnake.cca`
   (~12 occurrences across "type argument not within bounds" and "cannot be converted" errors).**
   `cardinal_components_version=5.2.2` (still pinned from 1.20.1) is the old
   `dev.onyxstudios.cca`-package release; Origins/Apoli on 1.21.1 now use a newer Ladysnake-namespaced
   release. Needs: find the real 1.21.1-compatible Cardinal Components version (same
   "check what Origins/Apoli itself pins" technique that found the Apoli/Calio group-id fix
   above — Cardinal Components isn't in Origins' own `gradle.properties` since it's bundled via
   Apoli/Calio's own transitive dependency, so check Apoli's or Calio's own build files instead),
   bump `cardinal_components_version`, and update every `import dev.onyxstudios.cca...` to
   `import org.ladysnake.cca...` in `OriginUtil.java`/`ArthropodPassiveTargetMixin.java`/
   `SeaCreaturePassiveTargetMixin.java`/`CharmedPassiveTargetMixin.java` (wherever
   `ComponentKey`/`OriginComponent` are used).

3. **Origins' own API changed: `Origin.getIdentifier()` no longer exists, `OriginLayers`/
   `OriginLayer` import path changed (~15 occurrences).** `io.github.apace100.origins.origin.OriginLayers`
   fails to resolve, and `origin.getIdentifier()` (used in `OriginUtil.hasOrigin`,
   `ArthropodPassiveTargetMixin`, `SeaCreaturePassiveTargetMixin`) is gone. Needs checking Origins'
   real 1.21.1 source (`apace100/origins-fabric` at tag `1.13.0-pre.3+mc.1.21.1`, same
   `gh api`/GitHub Contents API technique already used this session) for the real current
   class location and the replacement method name for getting an origin's ID.

4. **Vanilla enchantment API changed: `EnchantmentHelper.getLoyalty`/`getRiptide` no longer
   exist (~12 occurrences, `ThrownJavelin`/`ThrownMermaidTrident`/`ThrownPetrifyingTrident`/
   `HarpyJavelinItem`/`PetrifyingTridentItem`).** Minecraft 1.21 moved enchantment level lookups to
   a registry/`Holder<Enchantment>`-based API (matches the separate `ResourceKey<Enchantment>
   cannot be converted to Holder<Enchantment>` errors elsewhere in this list, and the vanilla-wide
   "everything is a `Holder<T>` now" pattern — see #7 below). Needs decompiling the real 1.21.1
   `EnchantmentHelper` class (same `javap`/CFR technique this project already uses throughout its
   CLAUDE.md gotchas) to find the real replacement call shape.

5. **`AttributeModifier`'s UUID-based constructor is gone (~7 occurrences,
   `FangItem`/`HarpyJavelinItem`/`PetrifyMobEffect` and others building weapon/effect attribute
   modifiers).** 1.21 changed `AttributeModifier` to be keyed by `ResourceLocation`, not `UUID` —
   every `new AttributeModifier(SOME_UUID, "name", value, operation)` call site needs updating to
   the new `ResourceLocation`-keyed constructor shape.

6. **`FoodProperties.Builder` lost `.saturationMod(float)` (1 occurrence so far, `ModItems.java` —
   likely more once earlier errors in the same file stop masking later ones).** 1.21 restructured
   `FoodProperties`'s builder API; needs checking the real current builder method names.

7. **Registry values are now wrapped in `Holder<T>` in more places — `MobEffect` (10x),
   `SoundEvent` via `playSound` overloads (8x total), `Enchantment` (2x).** A broad,
   version-wide Minecraft pattern (not specific to this mod) — direct registry object references
   in method signatures increasingly expect `Holder<T>` wrappers instead. Each call site needs
   updating to pass/accept the `Holder<T>` form; check each one against the real current vanilla
   method signature via `javap`/decompile rather than guessing a uniform fix, since not every
   occurrence may need identical treatment.

8. **`LivingEntity.getMobType()` no longer exists (~3 occurrences, `HarpyJavelinItem`'s undead
   check).** Minecraft's `MobType`-based undead-immunity system appears to have changed in 1.21 —
   needs checking the real current mechanism for "is this entity in the undead group" (this
   project's own CLAUDE.md already has a whole gotcha about `MobType.UNDEAD` from the 1.20.1 port,
   worth re-reading before guessing at the 1.21.1 replacement).

9. **Model/renderer signature changes: `renderToBuffer`/`render` (12x total),
   `Item#getDefaultAttributeModifiers` (2x), `ModelLoadingPlugin.Context#addModels` (2x),
   `TooltipContext` replacing a raw `Level` parameter in tooltip methods (4x),
   `TridentItem#getUseDuration`/`Player#startAutoSpinAttack` (8x total).** A cluster of
   individually-small rendering/item-API signature changes, affecting
   `HarpyJavelinRenderer`/`MermaidTridentRenderer`/`SerpentAegisRenderer`/`TridentStyleFlatModels`/
   `TridentStyleFlatIconMixin`/`MermaidCrownItem`/`HarpyJavelinItem`/`PetrifyingTridentItem`/every
   item overriding `appendHoverText`. Each needs its own real-signature check.

10. **`BleedMobEffect.applyEffectTick` no longer overrides `MobEffect.applyEffectTick` (2x) —
    likely a downstream consequence of #7's `Holder<MobEffect>` change** (the base class method
    signature itself may have changed to take a `Holder<MobEffect>` or similar, breaking the
    override). Needs the same real-signature check as #7 before assuming the fix.

11. **`EquipmentSlot is not a functional interface` (6x) — likely `EquipmentSlotGroup` replacing
    `EquipmentSlot` for multi-slot attribute-modifier application**, a real vanilla API addition in
    later 1.20.x/1.21 versions (lets one modifier apply across e.g. both hand slots at once) that
    may have changed the expected type in `Item.Properties#attributes`-style builder calls this
    project's weapon/armor items use.

### Recommended path for sub-project 2

Given the volume and variety here, this needs its own proper brainstorm/plan rather than being
tackled ad hoc — but the categorization above already does most of the scoping work. A reasonable
task decomposition, roughly in dependency order (each unblocks cleaner error output for the next):

1. Fix #1 (`ResourceLocation` factory method) — mechanical, huge count, no design decisions.
2. Fix #2 (Cardinal Components package/version) — unblocks the origin-check helper code.
3. Fix #3 (Origins' own `Origin`/`OriginLayers` API) — needs real source-checking, but is
   contained to a handful of files (`OriginUtil`, the two `*PassiveTargetMixin` classes).
4. Fix #4/#5/#7/#10 together — these are all "vanilla registry/enchantment API now uses
   `Holder<T>`" variants of the same underlying 1.21 pattern; likely faster to research once
   (decompile the real 1.21.1 vanilla classes) and apply consistently than to treat as 10 separate
   problems.
5. Fix #6/#8/#9/#11 — the remaining scattered individual signature changes, each small and
   independent, safe to batch or split across files however's convenient once the above are clear.
6. Re-run the build after each phase — the error count/pattern list will likely shrink and
   simplify as each category clears, possibly revealing errors currently masked by earlier ones in
   the same file (javac stops per-file after enough errors).
